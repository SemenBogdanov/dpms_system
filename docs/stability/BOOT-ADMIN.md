# Загрузки сервера: автоматический импорт и админка

## Scope и путь пользователя

Администратор открывает `/admin/users`, видит блок «Загрузки сервера», проверяет
состояние синхронизации и даты событий. Может выбрать период, перейти по
страницам и перечитать БД кнопкой обновления. Из интерфейса нельзя изменить
или удалить записи, перезагрузить VPS, запустить shell или выбрать путь файла.

Тестовый адрес неизменен: `http://localhost:55177/admin/users`.
Текущий этап готовится локально; production deploy требует отдельной команды.
Незавершённые изменения раздела «Графы» сохраняются без переработки.

## Доставка данных

1. Host systemd recorder создаёт один атомарный UTF-8 файл на загрузку VPS.
2. `server-boot-worker` стартует с контейнерами DPMS и затем проверяет каталог
   каждые 60 секунд. Открытие админки для импорта не требуется.
3. Каталог `/var/lib/dpms-boot-events` смонтирован только на чтение и только
   этому worker. Backend API не имеет доступа к файловой системе host.
4. Worker сохраняет структурированные поля в PostgreSQL DPMS. Уникальная пара
   `source_id + event_id` предотвращает дубли при повторе и конкуренции.
5. При недоступности БД файлы остаются на диске. Неудачная транзакция откатывается,
   следующая проверка повторяет импорт. Существующая запись не перезаписывается;
   изменение уже импортированного события отображается как конфликт.

Ни HTTP endpoint для загрузки событий, ни новый API-ключ не требуются.
Worker использует существующее подключение DPMS к БД, без чтения/публикации
конфигурационных секретов. Нет Docker socket, host network, root filesystem
mount или управления сервером из приложения.

## Данные и честность отчёта

- Отдельные поля: время загрузки VPS, время записи на диске, время импорта в БД.
- Uptime относится только к моменту записи, не является текущим uptime.
- Причина всегда «Не установлена». Нельзя называть количество загрузок числом
  аварий или считать по нему доступность приложения.
- Первый запуск recorder записывает текущую загрузку, даже если она произошла
  до установки. История более ранних загрузок неизвестна.
- API возвращает UTC; интерфейс показывает московское время с явным указанием.
- Фильтр по времени загрузки, не по времени импорта. По умолчанию все записи,
  чтобы давняя текущая загрузка не исчезала из начального экрана.
- Нет записей и нет свежей проверки importer — разные состояния. Состояния
  `waiting`, `ok`, `degraded`, `stale` показывают состояние доставки,
  не состояние всего DPMS. Stale после 180 секунд без проверки или при timestamp
  проверки более чем на 5 секунд в будущем (возможный откат часов).
- Ошибки файлов ограничены безопасными кодами/счётчиками. Сырые файлы, exception
  messages, hostnames, IP и конфигурации не выводятся в API и UI.

## Интеграция и релиз

- `GET /api/admin/server-boots`: серверный `require_role("admin")`, пагинация,
  `days=0` для всей истории или 1..366, `limit` до100.
- Production-ветка использует `097_server_boot_events` непосредственно после
  `096_graph_documents`. Незавершённые изменения Graphs не входят в релиз.
  В изолированном локальном кандидате ранее применена другая цепочка:
  `097_graphs_hierarchy_knowledge -> 098_server_boot_events`. Она не изменялась
  и не переносится на production. Перед будущим релизом Graphs нужна отдельная
  интеграция миграций; нельзя просто объединить эти две ветки Alembic или
  повторно создавать существующие boot-таблицы.
- Production compose использует только настоящий каталог host и source
  `primary-vps`. `create_host_path: false` не позволяет незаметно создать пустой
  каталог вместо отсутствующего recorder.
- Local compose использует только `deploy/stability/fixtures`, source
  `local-development`. Это синтетические события, не production history.
- Перед app promote release manager проверяет установленный host recorder;
  worker включён в promote, healthcheck и rollback. При откате на старый compose
  новый worker останавливается. Файлы host и записи БД не удаляются.
- Перед миграцией production нужен backup БД по действующему release protocol.
