# Outlook: Прямое Подключение PostgreSQL

## Контракт

Windows-клиент подключается к PostgreSQL напрямую через Npgsql, без обращения
к сайту DPMS с рабочего ноутбука. HTTPS остаётся отдельным совместимым режимом
для ранее созданных подключений. Новый режим выбран по умолчанию.

Требуются migration `101_mail_import_db_queue`, запущенный `mail-import-worker`,
отдельная ограниченная LOGIN-роль, доступный TCP-порт и доверенная TLS identity.
Успешный cross-build не подтверждает работу COM, DPAPI и сети на Windows.

Клиент вызывает только четыре schema-qualified функции:

- `mail_import_db_protocol()` проверяет версию и максимальный размер batch.
- `mail_import_db_connect(text,text)` подключает устройство по DB-login без кода.
- `mail_import_db_enqueue(text,uuid,text)` ставит batch в ограниченную очередь.
- `mail_import_db_status(text,uuid)` возвращает подтверждение после импорта.

Постановка в очередь не подтверждает доставку. Worker повторно проверяет владельца,
права и отзыв устройства, выполняет общий mail-import service и атомарно сохраняет
результат. Только итоговый ACK продвигает локальный checkpoint. Повтор запроса
с тем же ID и payload идемпотентен; другой payload отклоняется. После потери ACK
новая доставка также не создаёт дублей благодаря существующим source IDs.

Пределы: 32 MiB batch; один pending batch на устройство; четыре/128 MiB на владельца;
1 GiB глобально. Pending TTL 24 часа, terminal receipts хранятся 7 дней. После
завершения payload очищается. Очередь не хранит raw device secret.

## Подготовка Администратором

1. Проверить установленную revision101 и healthy worker.
2. Проверить, что app schema не доступна на CREATE клиенту/PUBLIC, а её таблицы,
   sequence и посторонние функции не доступны через PUBLIC. Схему не угадывать:
   она может отличаться от `public`.
3. В защищённой DBA-сессии выполнить
   `connectors/outlook-windows/provision-db-role.sql` с `app_schema`, новым
   `bridge_role`, UUID существующего пользователя DPMS `owner_id` и явными
   `include_body`/`include_attachments` (`true` либо `false`). Для текстов нужен
   `include_body=true`; файлы включаются отдельно. Script связывает DB-login
   с владельцем на сервере и отказывается переиспользовать существующую роль,
   выдаёт только CONNECT/USAGE/EXECUTE и проверяет эффективные права, включая
   отдельные колонки и PUBLIC grants во всех несистемных схемах текущей БД.
   Лишние права блокируют provisioning; существующие grants автоматически не меняются.
   Пароль задаётся интерактивной `\password`, не аргументом shell.
4. Настроить `hostssl`, SCRAM и сетевой ACL по согласованному корпоративному
   маршруту. Не открывать БД всем адресам. Не выдавать роль владельца приложения,
   SUPERUSER, CREATEROLE, членство в других ролях или доступ к таблицам.
5. Передать пользователю host, port, database, schema, username, пароль и при
   необходимости публичный CA через разрешённый закрытый канал. В EXE нет
   вшитых реквизитов; секреты не отправлять в чат/документацию.

TLS обязателен. По умолчанию действует `VerifyFull`: имя host должно совпадать с
сертификатом. При доверенном системном CA поле файла пустое; иначе выбирается
проверенный публичный CA-файл. Не использовать режим без проверки сервера
или чужой клиентский сертификат.

Для подключения по IP с 0.2.2 поддерживается точная проверка SHA-256 сертификата
сервера вместо проверки CA и имени. Администратор получает отпечаток на
доверенном сервере, завершающем TLS, из действующего публичного сертификата
(не из приватного ключа и не из непроверенного сетевого соединения):

```sh
# Печатает SHA-256 открытого сертификата, не выгружает ключ.
openssl x509 -in /path/to/public-server.crt -noout -fingerprint -sha256
```

В «SHA-256 сервера» вставляются только символы после знака `=`: 64 hex-символа
с двоеточиями между парами или без них. Поле «Сертификат CA» оставляют пустым.
При несовпадении или истечении срока сертификата вход блокируется. После
замены сертификата нужно повторно получить подтверждённый отпечаток;
для уже связанного EXE остановить синхронизацию, отвязать его локально и
переподключить с новым значением (отзыв старого устройства выполняется в DPMS).
Клиент блокирует неявные PGSSL client identity/CA files вместо молчаливого чтения.

## Рабочее Подключение

1. Получить разрешение на экспорт тестовой почты/вложений.
2. Запустить новый EXE, выбрать PostgreSQL, заполнить выданные параметры БД
   и имя устройства. Код подключения и открытие сайта DPMS не требуются.
3. Сначала нажать «Проверить соединение». Контроль TLS, входа и протокола
   DPMS ничего не регистрирует и не открывает Outlook.
4. Нажать «Подключить и начать импорт». Сервер определяет владельца по фактически вошедшему
   DB-login, возвращает имя и разрешённый объём данных; синхронизация запускается
   автоматически. «Пауза» останавливает автоматическую передачу.

Пароль БД и device secret сохраняются только в существующем DPAPI-хранилище
текущего пользователя Windows. Не используется пароль Outlook/Exchange.
Повтор одной попытки входа использует тот же идентификатор устройства.
DB-login нельзя перепривязать к другому владельцу запросом клиента; изменение
серверной привязки выполняет администратор. Неизвестный или отключённый DB-login
не получает доступ к почте. DB-device secret не заменяет HTTPS bearer.

## Приёмка И Откат

Synthetic gates: протокол C#, disposable PostgreSQL, SQL privilege negatives,
queue retry/revoke/atomicity, worker health/lifecycle, TLS host/CA negatives,
сквозной Npgsql -> SQL -> worker -> ACK, Windows cross-build.

На рабочем Windows отдельно проверить разрешённые тестовые письмо/вложение/встречу,
повтор sync без дублей, паузу, отзыв, offline/reconnect, COM prompts, DPAPI,
автозапуск, tray exit, DPI150/200%. Реальную почту для автоматических QA не читать.

App rollback сохраняет queue/receipts/schema101; controller останавливает новый
worker и отключает restart policy, если старый compose его не содержит. Downgrade
или удаление очереди с данными запрещены без отдельного решения. Provisioning роли
и Windows TLS acceptance не считаются выполненными по одному server deploy.
