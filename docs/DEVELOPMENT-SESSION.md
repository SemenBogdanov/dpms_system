# DPMS: обязательный протокол сессии разработки

Решение пользователя: 26.10.2026. Область: source code, тесты и проектные документы
DPMS с настроенным Git remote. История хранится в Git, не в Docker images или
постоянных каталогах на каждый выпуск. Сохранение WIP не означает его готовность.

## Начало сессии

1. Прочитать `AGENTS.md` и актуальный project control layer PersonalOS.
   Рабочий путь брать из поля `active worktree` в `02 Projects/dpms/PROJECT.md`,
   не из исторического `code repo path` и не по названию каталога или ветки.
   Сверить `git rev-parse --show-toplevel`, `git worktree list --porcelain`
   и `git rev-parse --git-common-dir`. Общий `.git` может находиться в другой
   рабочей папке; это не делает её источником текущего релиза. Если путь не задан,
   отсутствует или не совпадает, остановиться и уточнить контекст, без fallback.
2. Зафиксировать repo/worktree, текущую ветку, HEAD и исходный dirty status.
   Отделить свой scope от существующих изменений, не сбрасывать чужой WIP.
3. Обновить сведения о remote: `git fetch origin`. Проверить upstream и
   `git rev-list --left-right --count HEAD...@{upstream}` при наличии upstream.
   Если upstream отсутствует, явно выбрать целевую remote branch до push.
   Зафиксировать baseline SHA точного destination `refs/heads/<TARGET_BRANCH>`
   через свежий `git ls-remote` либо ожидаемое отсутствие согласованной новой ветки.
4. Обновлять только выбранную активную рабочую папку, когда это входит в scope,
   и только fast-forward при clean status. Старый локальный `main` в другом
   worktree не обновлять ради синхронизации текущей сессии. При dirty status или
   divergence сначала разобрать свой scope, не выполнять blind pull, reset,
   rebase чужой истории или автоматический force push.
5. Указать verification commands, границы задачи и способ сохранения WIP.
   Проверка metadata не доказывает целостную интеграцию или работоспособность.

## Завершение сессии

1. Выполнить scoped review и соответствующие риску тесты. Для docs-only правок
   допустимы проверка diff, ссылок и правил; не заявлять неисполненный runtime QA.
2. Проверить явный список публикуемых путей и весь ещё не опубликованный delta.
   Удалённый в HEAD секрет мог остаться в промежуточном commit: его наличие
   блокирует публикацию всей такой цепочки до отдельного безопасного решения.
3. До staging определить уже staged scope по metadata. Чужие или непроверенные
   staged-изменения не включать в commit, не сбрасывать и не перезаписывать чужой
   index. Добавить только проверенные изменения своего scope и проверить staged
   diff только в allowlist. Если свой scope нельзя изолировать, остановиться
   до commit. После успешного staged review создать commit только согласованного
   scope. Не использовать `git add .`/`git add -A` как замену review.
4. Зафиксировать проверенный полный source/snapshot commit SHA для публикации.
   `HEAD` использовать только когда публикуется именно текущий HEAD. Snapshot,
   созданный без checkout, имеет собственный SHA; менять HEAD для сверки не нужно.
   Непосредственно перед push повторно сверить точный destination ref с baseline.
   При concurrent remote change, включая появление или исчезновение ветки,
   остановиться и пересмотреть публикацию, без force, blind merge или retry.
   Выполнить обычный push с явными source SHA и destination:

```sh
git -c push.followTags=false push origin <FULL_SOURCE_SHA>:refs/heads/<TARGET_BRANCH>
```

Не использовать `--all`, `--mirror`, `--tags` или автоматический follow-tags.
Отказ push означает stop/review, не разрешение ослабить проверки. Изменения
не мержатся в `main` только ради синхронизации; feature/WIP/archive имеют
собственный статус.

5. Свежим запросом сверить ожидаемый полный source/snapshot SHA с объявленной
   сервером вершиной точного destination ref:

```sh
git ls-remote --exit-code origin refs/heads/<TARGET_BRANCH>
```

Результат должен содержать ровно ожидаемый ref и тот же `<FULL_SOURCE_SHA>`,
не обязательно текущий HEAD. При несовпадении остановиться, не повторять push
автоматически. Проверить также `git status --short --branch`; ahead/behind
проверять для публикуемой ветки с upstream после обновления tracking refs.
Для snapshot без checkout подтвердить неизменность рабочего HEAD и index.
Локальный `origin/...`, успешный push или clean status по отдельности не заменяют
свежую сверку remote SHA. При нескольких refs учитывать успех каждого отдельно.

6. Зафиксировать source ref/snapshot SHA, destination ref, remote SHA, проверки, статус dirty-остатка
   и ссылки на намеренно исключённые runtime/data зоны без их содержимого.
7. Обновить project `LOG.md`/статус. Различать source commit, проверенный
   local candidate и deployed release: docs commit не является новым app release.

## Незавершённая работа

- Различать синхронизацию текущего согласованного scope и сохранность исторического
  WIP в других worktrees. Учтённый старый остаток не требует его merge, checkout,
  удаления или изменения ради завершения текущей сессии. Общую сохранность всех
  рабочих папок нельзя выводить из синхронизации одного scope.
- Безопасный, проверенный на допустимость публикации WIP сохранять в именованной
  `wip/<scope>-<date>` либо `archive/<scope>-<date>` ветке и сверять её remote SHA.
- В архиве указывать baseline, scope, причину незавершённости и ограничения.
  Архивный snapshot может быть неработоспособным и не предназначается для deploy.
- Для сохранности требуются достижимый commit и опубликованный ref. Один blob
  где-либо в object database не является snapshot с нужными путями и file modes.
- Нельзя удалять исходный WIP, пока не проверены соответствие snapshot и remote,
  runtime references, а также сохранность не относящихся к Git данных.
- При невозможности публикации оставить содержимое на месте, сообщить
  `не синхронизировано` и причину. Не скрывать остаток в бессрочном stash.

## Безопасность

Repo публичный; публикация source и публикация секретов не равнозначны.
`.env*`, private keys, tokens, credential stores, базы, uploads и runtime data
не включаются в Git. Исключение из Git должно быть явным, а не маскироваться
под отсутствие нужных изменений. Secrets никогда не переносить в отчёт.

Перед content review или scanner сначала определить разрешённый allowlist.
Не выполнять рекурсивный поиск секретов по всему workspace и не читать
запрещённые файлы. Если для source/config нужен отдельный approval, получить
его до проверки. Scanner не должен отправлять найденные значения в сеть.
Потенциальный secret блокирует push до классификации без вывода значения.

Force push, переписывание опубликованной истории, удаление remote branches,
production deploy и DB operations не разрешаются обычным Git-sync gate.

## Критерий готовности

Сессия с изменениями source завершена как **синхронизированная**, только если
её согласованный scope проверен, сохранён commit и его полный source/snapshot SHA
подтверждён в точном destination ref; весь оставшийся dirty/unpublished WIP явно учтён.
Невыполненный пункт означает `не синхронизировано` или `частично синхронизировано`,
а не «всё готово». Read-only проверка без изменений не требует искусственного commit.
