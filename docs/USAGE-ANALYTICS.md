# Аналитика использования DPMS

## Область

Кандидат от 27.09.2026 принят пользователем 02.10.2026 с разрешением на deploy.
Экран `/admin/usage` открывается из
администрирования сотрудников или интеграций. Доступ к отчёту только у
системного `admin`; `teamlead` не получает его через рабочие полномочия.
Разрешение на текущий production release получено; результат выпуска фиксируется
в проектном журнале. Этот документ сам по себе не подтверждает завершение deploy.

## Значение показателей

- Вход: существующее серверное событие `login_success` после успешной проверки
  учётных данных. Восстановление сохранённой сессии и фоновые запросы не входы.
- Посещение: открытие раздела в видимой вкладке или переход из другого раздела.
  Смена объекта, query-параметров, фильтров и перезагрузка того же раздела в той
  же вкладке не добавляют посещение. Возврат из другого раздела добавляет.
- Счётчики пользователей: уникальные учётные записи соответствующего типа
  событий в выбранном периоде, а не количество устройств и не время работы.
- Популярность: число зарегистрированных переходов, а не длительность работы,
  производительность сотрудника или факт выполнения задачи.
- Даты включительны, часовой пояс `Europe/Moscow`, максимум 366 дней.
  Фильтр сотрудника относится только к журналу входов, не ко всей сводке.
- Первый вход / первое посещение означают самые ранние сохранённые записи.
  Это не доказательство полноты истории. Посещений до установки сборщика нет;
  клиент без сети, старый открытый frontend или запрет хранилища могут давать
  неполные данные. До первой записи интерфейс не изображает нулевую активность.

## Данные и доступ

Используется существующая `activity_events`, без новой таблицы или миграции.
Старые `login_success` не переписываются. Их прежний User-Agent используется
только для приблизительной классификации устройства, ОС и браузера. Точную
модель телефона определить нельзя; iPad с desktop User-Agent может выглядеть
как Mac. Неизвестные значения обозначаются явно.

Новые `usage_section_view` содержат только ID учётной записи, серверное время и
идентификатор раздела из разрешённого списка. Не записываются URL, параметры,
названия документов/графов, сообщения, IP или содержимое страниц. API отчёта
не возвращает IP и исходный User-Agent старых событий. Старый API активности
также исключает входы и посещения для всех, кроме системного admin.

Клиентский UUID преобразуется в серверный UUID с пространством имён пользователя.
Повтор запроса не создаёт дубликат и не изменяет исходную запись. Лимит приёма
считается по пользователю, а не общему офисному IP. Клиент не опрашивает сервер
таймером; ошибка отправки аналитики не вызывает выход из системы.

Сводка формируется SQL-агрегатами в одном снимке PostgreSQL. Детальный журнал
пагинирован; персональные исходные метаданные выбираются только для текущей
страницы и не включаются в ответ. Автоматическое удаление истории в этом
кандидате не вводится. Политика хранения и отдельные индексы при росте нагрузки
требуют отдельного решения и измерений.

## API

- `POST /api/usage/section-views`: `{event_id, section}`, активная сессия,
  серверная проверка доступа к разделу, ответ 204.
- `GET /api/admin/usage`: `start_date`, `end_date`, `limit`, `offset`,
  необязательный `user_id`; только системный admin.

## Локальный контур

Origin остаётся **http://localhost:55177**, графы остаются `/graphs`.
Не пересобирать frontend из старого `dpms-graphs-interactions`: там нет принятого
исправления 2.8 для тачпада. Исходник текущего кандидата:
`/Users/bogdanov/Code/dpms-graphs-acceptance-release`.

Существующая локальная БД имеет старую цепочку миграций с head
`098_server_boot_events`, production имеет `099_graphs_hierarchy_knowledge`.
Структура журнала событий совместима. Для локального кандидата предусмотрен
`deploy/local-usage.override.yml`: новый backend без запуска миграций и seed.
Данные и revision локальной БД не переписываются. Этот override нельзя применять
в production; штатный release использует обычную цепочку миграций.

При локальном Compose запуске сохранять `DPMS_FRONTEND_PORT=55177`,
`DPMS_BACKEND_PORT=58005`, `DPMS_DB_PORT=55436`. Обновлять только нужный сервис
через `up -d --no-deps --no-build`; не пересоздавать всю группу сервисов.
Backend runtime проверен через `/health` на58005; frontend обращается к нему
внутри Docker через `backend:8000`.

Изолированные backend-тесты запускаются только в БД с именем
`dpms_usage_test_*`; URL передаётся средой и не печатается. Не направлять тесты
на рабочую локальную или production БД.

## Приёмка

Автоматическая проверка кандидата от27.09.2026: backend21PASS (4 PostgreSQL),
browser45PASS (Chromium/WebKit/iPhone), graph2.8 regression10PASS,
boot-admin regression27PASS. Пять ширин320–1920px и light/dark/rose проверены.
Независимый critic: APPROVE после исправления privacy bypass через
employee-summary и разрешения `profile`. Build/scopedESLint/diff-check PASS.

1. Admin: открыть `/admin/usage`, выбрать 3 дня или собственный период.
2. Сверить сводку и раскрыть журнал входов: время МСК, сотрудник, устройство,
   браузер/ОС; проверить фильтр сотрудника и страницы.
3. Перейти в другой раздел, вернуться, обновить отчёт: переход учтён. Простая
   перезагрузка текущего раздела не должна добавлять посещение.
4. Войти заново: добавляется один успешный вход. Открытие уже действующей сессии
   не является новым входом.
5. Обычный сотрудник и teamlead: отчёт недоступен, прямой GET возвращает 403.
6. Проверить мобильный экран и light/dark/rose; графы 2.8 остаются без изменений.
