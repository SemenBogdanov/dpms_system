# Раздел «Графы» в DPMS

## Текущий слайс

Первый кандидат встраивает проверенный standalone-прототип как отдельный раздел
DPMS по маршруту `/graphs`. Основная оболочка сохраняет навигацию и учётную
запись DPMS, а рабочее пространство исполняется из статического same-origin
snapshot `frontend/public/graph-workspace/index.html`.

Исходный прототип:

```text
/Users/bogdanov/Code/dpms-graphs-prototype/index.html
```

Snapshot намеренно изолирован от React-кода. Это позволяет перенести текущий UX
без частичной переписи и сохраняет границу для будущего самостоятельного
приложения. Same-origin `postMessage`-мост передаёт только операции хранилища;
токен сессии остаётся в React-оболочке и не передаётся внутрь iframe.

## Данные и доступ

- раздел доступен каждому авторизованному пользователю;
- пункт можно переставлять или скрывать через существующий конфигуратор меню;
- каждый новый, дублированный или импортированный граф по умолчанию остаётся
  локальным для браузерного профиля;
- локальные данные хранятся в `localStorage` с разделением по `user.id`;
- локальный workspace имеет версию схемы `3`; данные схемы `2` автоматически
  копируются в новый изолированный ключ при первом открытии, а исходный ключ
  остаётся резервной копией;
- системные графы хранятся в общей БД, но доступны только владельцу. Роль admin
  не даёт обхода этого ограничения;
- изменение графа никогда не вызывает фоновую отправку на backend;
- в списке графов пользователь явно публикует локальный граф стрелкой вверх;
  повторное нажатие обновляет его системный snapshot;
- системный snapshot загружается стрелкой вниз как локальная рабочая копия и не
  перезаписывает одноимённый локальный граф;
- удаление локальной копии не удаляет системный snapshot. Удаление snapshot
  является отдельным явным действием;
- импортированный файл не отправляется на backend до явной публикации;
- совместное редактирование и наследование прав связанных сущностей не входят в
  текущий слайс.

API использует `client_id` графа и оптимистическую блокировку `revision`. Повтор
идентичного запроса идемпотентен. При конфликте серверная версия не
перезаписывается. При сетевой ошибке публикации рабочая локальная версия остаётся
без изменений и может быть отправлена повторно.

Backend принимает сохранённые документы схем `2` и `3`. Схема `3` добавляет
стикеры, списки, атомы, ручные размеры и маршрутизацию связей; чтение прежних
серверных snapshot схемы `2` сохраняется.

## Взаимодействие с холстом

- режим линзы отсутствует; при наведении на элемент подсвечиваются сам элемент,
  его непосредственные связи и соседи;
- `Space + ЛКМ` перемещает холст, drag с пустого места создаёт рамку
  множественного выделения;
- стикер создаётся отдельным инструментом. `Tab` во время ввода завершает его и
  создаёт следующий стикер того же вида;
- `Shift + Tab` создаёт дочерний элемент, `Shift + S + Tab` — соседний;
- мастер иерархий принимает outline: новая строка создаёт элемент, а `Tab` или
  два пробела задают уровень вложенности; `Ctrl/⌘ + Enter` строит граф;
- сочетания для мастера, дочернего и соседнего элементов, стикеров, автоукладки,
  показа всего графа и панелей можно изменить в справке;
- ручной размер меняется за правую, нижнюю или угловую ручку либо числовыми
  полями в инспекторе. При включённом `Авто` размер определяется числом связей и
  ручки скрываются;
- линии поддерживают плавный, ортогональный и ломаный маршруты. Двойной клик по
  выбранной линии добавляет редактируемую точку;
- связь создаётся `Shift + drag`; рядом с целевым элементом действует мягкое
  магнитное прилипание;
- сущность `Список` можно разложить в отдельные связанные атомы;
- trackpad pinch и `Shift + колесо` изменяют масштаб; на обзорном масштабе
  элементы отображаются компактными кругами.

Общие структурные лимиты локального редактора и серверного хранилища:

- до 100 графов на пользователя;
- до 1500 элементов и 3000 связей в одном графе.

Локальный редактор ограничивает один граф 5 МБ и дополнительно учитывает
фактическую квоту `localStorage`, заданную браузером. Сервер принимает до 5 МБ
на граф и до 50 МБ суммарно на пользователя. При отказе локальной записи
изменение откатывается в интерфейсе, поэтому несохранённое состояние не выглядит
как сохранённое.

API:

```text
GET    /api/graphs
GET    /api/graphs/{client_id}
PUT    /api/graphs/{client_id}
DELETE /api/graphs/{client_id}?base_revision=N
```

## Проверка snapshot

Канонический встроенный snapshot находится в
`frontend/public/graph-workspace/index.html`. После изменения обязательны:

```bash
cd frontend
npm run build
npm run smoke:navigation
npm run test:graphs
```

Затем проверяются `/graphs`, импорт JSON, сохранение после reload, desktop и
iPhone layout. Production deploy выполняется только после отдельного разрешения.

Перед локальным запуском backend применяется миграция
`096_graph_documents`. Откат миграции удаляет только таблицу серверных графов и
не затрагивает локальные копии в браузерах.

## Следующая архитектурная граница

При развитии отдельного приложения статический snapshot заменяется версионируемым
frontend package или отдельным origin. Перед сменой origin потребуется отдельный
контракт доверенных origins для `postMessage` и явная миграция локальных графов:
новый origin не получит автоматический доступ к текущему `localStorage`.
