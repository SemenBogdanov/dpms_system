# Раздел «Графы» в DPMS

## Текущий слайс

Первый кандидат встраивает проверенный standalone-прототип как отдельный раздел
DPMS по маршруту `/graphs`. Основная оболочка сохраняет навигацию и учётную
запись DPMS, а рабочее пространство исполняется из статического same-origin
snapshot `frontend/public/graph-workspace/index.html`.

Исходный прототип:

```text
/Users/bogdanov/Code/dpms-graphs-prototype/index.html
```

Snapshot намеренно изолирован от React-кода. Это позволяет перенести текущий UX
без частичной переписи и сохраняет границу для будущего самостоятельного
приложения. Same-origin `postMessage`-мост передаёт операции хранилища и тему оболочки;
токен сессии остаётся в React-оболочке и не передаётся внутрь iframe.

## Данные и доступ

- раздел доступен каждому авторизованному пользователю;
- пункт можно переставлять или скрывать через существующий конфигуратор меню;
- каждый новый, дублированный или импортированный граф по умолчанию остаётся
  локальным для браузерного профиля;
- локальные данные хранятся в `localStorage` с разделением по `user.id`;
- локальный workspace имеет версию схемы `3`; данные схемы `2` автоматически
  копируются в новый изолированный ключ при первом открытии, а исходный ключ
  остаётся резервной копией;
- системные графы хранятся в общей БД, но доступны только владельцу. Роль admin
  не даёт обхода этого ограничения;
- изменение графа никогда не вызывает фоновую отправку на backend;
- в списке графов пользователь явно публикует локальный граф стрелкой вверх;
  повторное нажатие обновляет его системный snapshot;
- системный snapshot загружается стрелкой вниз как локальная рабочая копия и не
  перезаписывает одноимённый локальный граф;
- удаление локальной копии не удаляет системный snapshot. Удаление snapshot
  является отдельным явным действием;
- импортированный файл не отправляется на backend до явной публикации;
- совместное редактирование и наследование прав связанных сущностей не входят в
  текущий слайс.

API использует `client_id` графа и оптимистическую блокировку `revision`. Повтор
идентичного запроса идемпотентен. При конфликте серверная версия не
перезаписывается. При сетевой ошибке публикации рабочая локальная версия остаётся
без изменений и может быть отправлена повторно.

Backend принимает сохранённые документы схем `2` и `3`. Схема `3` добавляет
стикеры, списки, атомы, ручные размеры, маршрутизацию связей и настройку линзы
для каждого представления; чтение прежних серверных snapshot схемы `2`
сохраняется.

## Взаимодействие с холстом

- переключатель `Линза связей` расположен в блоке `Представление` и по умолчанию
  выключен. При включении наведение или одиночное выделение подсвечивает сам
  элемент, его непосредственные связи и соседей; настройка сохраняется отдельно
  для каждого представления;
- `Space + ЛКМ` перемещает холст, drag с пустого места создаёт рамку
  множественного выделения;
- стикер создаётся отдельным инструментом. `Tab` во время ввода завершает его и
  создаёт следующий стикер того же вида;
- `Shift + Tab` создаёт дочерний элемент, `Shift + S + Tab` — соседний;
- мастер иерархий принимает outline: новая строка создаёт элемент, а `Tab` или
  два пробела задают уровень вложенности; `Ctrl/⌘ + Enter` строит граф;
- мастер и режим `Иерархия` используют одну раскладку: родитель, его ветка,
  следующий сосед. Порядок элементов берётся из документа графа, а не из числа
  связей или текущих координат. После радиальной укладки или компактной сетки
  выбор `Иерархия` восстанавливает порядок и вложенность; отступы учитывают
  размеры элементов. Выбор укладки сразу применяет её и отменяется одним undo;
- мастер раскладывает только добавленные элементы. Автоукладка сохраняет
  закреплённые элементы и внутреннюю геометрию групп. Для произвольного графа
  с несколькими родителями выбирается первая входящая связь, с приоритетом
  связи `дочерний`; циклы обходятся один раз. Все связи остаются в документе;
- длинная укладка целиком сдвигается в сохраняемый диапазон координат без
  изменения расстояний. Если она не помещается, операция отклоняется до
  изменения графа: координаты не обрезаются при повторном открытии;
- сочетания для мастера, дочернего и соседнего элементов, стикеров, автоукладки,
  показа всего графа и панелей можно изменить в справке;
- ручной размер меняется за любую из пяти точек на каждой стороне прямоугольника
  или угловую ручку, а также числовыми полями в инспекторе (2.4). `Shift + drag`
  из точки начинает связь. При включённом `Авто` размер определяется числом
  связей и ручки изменения размера скрываются;
- линии поддерживают плавный, ортогональный и ломаный маршруты. Двойной клик по
  выбранной линии добавляет редактируемую точку;
- связь создаётся `Shift + drag`; виден пунктирный предварительный маршрут,
  рядом с целевым элементом действует мягкое магнитное прилипание (2.5–2.6).
  Выбранные порты сохраняются вместе с графом;
- сущность `Список` можно разложить в отдельные связанные атомы; растяжение
  вниз открывает дополнительные строки вместо фиксированных четырёх (2.7);
- обычное колесо и trackpad pinch изменяют масштаб. В блоке `Представление`
  есть `Инверсия колеса`; она не инвертирует pinch (2.8). На обзорном масштабе
  элементы отображаются компактными кругами;
- тема light/dark/rose поступает из DPMS без перезагрузки рабочего пространства.
  Отдельного переключателя темы внутри графа нет (3.1).

## Импорт и справка

Пункт 2.12: меню файла → `Импорт JSON` → `Выбрать JSON` → `Формат данных`.
Диалог поддерживает пять режимов: родной документ DPMS, `Кубики`, дерево
произвольного JSON, таблица записей и список связей. Автоопределение можно
переопределить; для записей/связей доступны пути и сопоставление полей.
Предпросмотр показывает результат и замечания до подтверждения. Создание
локального графа не публикует его в систему. Некорректный JSON или структурные
лимиты не удаляют текущий граф. Подробнее: [JSON-IMPORT.md](JSON-IMPORT.md).

Пункт 2.3: опубликованная статья `graphs-hierarchy-guide` в Базе знаний открывается
из мастера иерархий по ссылке `База знаний`. Исходник справки:
[HIERARCHY-GUIDE.md](HIERARCHY-GUIDE.md). Статья содержит только реализованный
outline-синтаксис, горячие клавиши, правила формирования связей и ограничения.

Общие структурные лимиты локального редактора и серверного хранилища:

- до 100 графов на пользователя;
- до 1500 элементов и 3000 связей в одном графе.

Локальный редактор ограничивает один граф 5 МБ и дополнительно учитывает
фактическую квоту `localStorage`, заданную браузером. Сервер принимает до 5 МБ
на граф и до 50 МБ суммарно на пользователя. При отказе локальной записи
изменение откатывается в интерфейсе, поэтому несохранённое состояние не выглядит
как сохранённое.

API:

```text
GET    /api/graphs
GET    /api/graphs/{client_id}
PUT    /api/graphs/{client_id}
DELETE /api/graphs/{client_id}?base_revision=N
```

## Проверка snapshot

Канонический встроенный snapshot находится в
`frontend/public/graph-workspace/`: `index.html` и локальные модули
`edge-routing.mjs`, `connection-ports.mjs`, `import-adapters.mjs`.
Единственная пользовательская ссылка проверки с 24.09.2026:
**http://localhost:55177/graphs** (пункт 1). Playwright использует этот же
пересобранный Docker-кандидат, а не отдельный preview-сервер.
После изменения обязательны:

```bash
cd frontend
npm run build
npm run smoke:navigation
npm run test:graphs
```

Затем проверяются `/graphs`, импорт JSON, сохранение после reload, desktop и
iPhone layout. Production deploy выполняется только после отдельного разрешения.

В актуальной release-цепочке после `096_graph_documents` и boot-миграций
`097_server_boot_events`, `098_server_boot_guide` применяется
`099_graphs_hierarchy_knowledge`. 099 добавляет статью, не перезаписывая
существующую пользовательскую редакцию. Откат 096 удаляет таблицу серверных
графов и не затрагивает локальные копии в браузерах; такой откат требует
отдельного решения, а не используется для обычного обновления.

Локальная экспериментальная БД на 55177 имеет другую историческую цепочку
097 Graphs -> 098 boot events. Не применять к ней release head и не менять
её Alembic stamp автоматически. При публикации используется clean release
worktree поверх production; пользовательские localStorage и документы не переносятся.

### Ограничение отката после новых сохранений

Пункты 2.1 и 2.4 расширяют payload полями `connectionLensEnabled`, `sourcePort`
и `targetPort`. Backend до этого релиза отвергает новые поля при чтении cloud
snapshot, а старый frontend способен удалить их при повторном сохранении даже
локального графа. После начала использования нового UI нельзя выполнять обычный
app rollback к 8457a3e или более ранней версии. Применяется forward-fix с сохранением
совместимой схемы и обработки этих полей на frontend/backend. Не переписывать
пользовательские JSON и localStorage ради отката. Restore БД и удаление данных
требуют отдельного разрешения и не входят в обычный release protocol.

Резервная копия до релиза нужна для disaster recovery, но не заменяет этот
compatibility gate: после снимка могли появиться новые пользовательские данные.

Оригинал и актуальный статус приёмки:
[ACCEPTANCE-2026-09-24.md](ACCEPTANCE-2026-09-24.md).
Пункт 3.2 оставлен пользователем в бэклоге.

## Следующая архитектурная граница

При развитии отдельного приложения статический snapshot заменяется версионируемым
frontend package или отдельным origin. Перед сменой origin потребуется отдельный
контракт доверенных origins для `postMessage` и явная миграция локальных графов:
новый origin не получит автоматический доступ к текущему `localStorage`.
