# Журнал загрузок сервера DPMS

Статья для встроенной базы знаний с полными листингами и памяткой переноса:
[Перенос DPMS: журнал загрузок VPS](../../docs/stability/BOOT-JOURNAL-GUIDE.md).
Неизменяемый снимок добавляется в БД миграцией `098_server_boot_guide`.

Первый этап стабильности по уточнению пользователя от 24.09.2026. Это небольшой
независимый Python-скрипт на Linux VPS, не worker внутри Docker. Он запускается
systemd при каждой загрузке и завершает работу; постоянно работающего процесса,
сети, БД, API и дополнительных Python-пакетов не требует.

## Что записывается

Постоянный каталог: `/var/lib/dpms-boot-events/`.
Один UTF-8 файл `boot-<event_id>.txt` на один kernel boot ID. Внутри время
загрузки и записи в UTC, uptime на момент записи, hash идентификатора загрузки,
`reason=unknown`. IP, hostname, пользователи, secrets и журналы приложения
не читаются и не сохраняются. Для локального времени прибавьте нужное смещение;
UTC не зависит от настройки часового пояса VPS.

Файл сначала полностью записывается и синхронизируется, затем атомарно
публикуется без перезаписи; синхронизируются также каталог журнала и его
родитель. Для нестандартного `--directory` родитель должен уже существовать.
Повторный запуск, restart service или два
одновременных запуска не создают дубликаты и не изменяют первую запись.
Перезапуск backend/Docker не создаёт новый boot ID и не считается загрузкой VPS.
Запускать recorder нужно на host: Linux VM Docker Desktop не является VPS.

При первом включении фиксируется текущая загрузка, в том числе произошедшая
до установки. Это не выдаётся за новое событие или полную прошлую историю.
Плановая перезагрузка, авария и включение после выключения пока не различаются.
Причину нужно сопоставлять с журналом ОС; этот скрипт её не выдумывает.
Время берётся из часов ОС: до NTP-коррекции оно может быть неточным.

## Установка на VPS после отдельного разрешения deploy

Это отдельный host-only release. Его установка не требует `prepare/promote`
приложения, пересборки Docker, миграции БД или reboot. Перед установкой проверить
health приложения, отсутствие конфликтующей службы и контрольные суммы файлов
из зафиксированного Git commit. При обновлении уже установленной версии сначала
сохранить старый скрипт и unit; при неудачной проверке восстановить их.

Из корня проверенного release checkout на сервере:

```bash
sudo install -d -m 0755 /opt/dpms-monitor
sudo install -m 0644 deploy/stability/record_boot.py /opt/dpms-monitor/record_boot.py
sudo install -m 0644 deploy/stability/dpms-boot-record.service /etc/systemd/system/dpms-boot-record.service
sudo systemd-analyze verify /etc/systemd/system/dpms-boot-record.service
sudo systemctl daemon-reload
sudo systemctl enable --now dpms-boot-record.service
```

Обработчик запускается от root с ограничениями systemd. Каталог создаёт
`StateDirectory`, доступ root и group root, файлы 0640. Каталог находится вне
release checkout и контейнера; обновления приложения его не удаляют.
Не нужно добавлять Docker socket, sudo API или доступ к secrets.
Ошибка записи видна в systemd/journal; максимум три старта за 120 секунд.
`active (exited)` после выполнения означает успех одноразового обработчика,
а не остановку наблюдения: при следующей загрузке systemd выполнит его снова.

## Посмотреть состояние и недельный отчёт

```bash
sudo systemctl status dpms-boot-record.service --no-pager
sudo journalctl -u dpms-boot-record.service -n 20 --no-pager
sudo python3 /opt/dpms-monitor/record_boot.py --report --days 7
sudo ls -lt /var/lib/dpms-boot-events
```

`--report` только читает события, ничего не создаёт. Можно перенаправить его
stdout в текстовый файл. Количество — обнаруженные загрузки, не доказанные
аварии и не показатель uptime. Отсутствие записей не означает стабильность.
Не перезагружать production только ради проверки без отдельного разрешения.

## Проверка без перезагрузки сервера

```bash
python3 -m unittest discover -s deploy/stability -p 'test_record_boot.py' -v
```

Тесты используют временные каталоги и синтетические kernel counters. Проверяют
один boot/повтор/два boot/конкурентность/ошибку публикации/недельный отчёт.
Локальная проверка 24.09.2026: финальные **20/20 PASS** на macOS и Linux/Python 3.11;
предшествующие 18/18 также прошли на Ubuntu 24.04.
`systemd-analyze verify` на Ubuntu 24.04 завершился без ошибок. Проверочный
контейнер удалён. Эти локальные проверки не заменяют проверку activation service
на целевом VPS. Результат каждой установки фиксируется отдельно в deployment log.
Read-only critic обнаружил недостающий fsync родительского каталога при первой
записи. Исправление внесено интегратором: родитель синхронизируется при создании
и повторе, новые тесты это проверяют. Прочих подтверждённых findings не осталось.
Для проверки установленного service: повторный `systemctl restart` должен
сообщить `already_recorded`; число событий не увеличится. Это проверяет
дедупликацию, но не является проверкой настоящего reboot.

## Откат и следующий этап

```bash
sudo systemctl disable --now dpms-boot-record.service
```

Скрипт и журнал можно оставить. Файлы автоматически не удаляются.
Сам host recorder фиксирует только загрузки VPS, не падение приложения без
перезагрузки и не простои сети. Автоматический перенос этих файлов в PostgreSQL
и read-only показ в админке описаны в `docs/stability/BOOT-ADMIN.md` и требуют
отдельного app release. Периодические замеры доступности/ресурсов ещё не реализованы.
